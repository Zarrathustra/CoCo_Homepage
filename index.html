CryoSieve

An advanced particle sorting and sieving solution for single-particle cryo-EM analysis. CryoSieve eliminates unnecessary particles from final stacks, producing cleaner density maps with measurably higher resolution.

v1.3.0

What it does

CryoSieve is an advanced software solution designed for particle sorting and sieving in single-particle analysis for cryo-EM. Supported by extensive experimental results, it has demonstrated superior performance compared to other cryo-EM particle sorting algorithms. For certain datasets, the precision of CryoSieve's particle subset selection approaches the theoretical limit.

  • Iterative sieving across multiple rounds with progressively refined density maps
  • Superior particle retention ratio compared to alternative sorting algorithms
  • Multi-GPU support for accelerated processing of large particle stacks
  • Resolution improvement that approaches theoretical limits for select datasets

Validated on publicly available cryo-EM datasets from EMPIAR:

Dataset Particles Mass (kDa) Source
TRPA143,585688EMPIAR-10024
Hemagglutinin130,000150EMPIAR-10097
LAT1250,712172EMPIAR-10264
pfCRT16,905102EMPIAR-10330
TSHR-Gs41,054125EMPIAR-11120
TRPM842,040513EMPIAR-11233
Apoferritin382,391440EMPIAR-10200
Streptavidin23,99152EMPIAR-10269

How it works

The sieving process involves iterative rounds of 3D reconstruction and particle filtering. In each round, CryoSieve analyzes the reconstructed density map, identifies particles that degrade the final resolution, and removes them. The high-pass cutoff frequency typically increases with each iteration, progressively refining the particle subset.

How it fits in CoCo

Create a CryoSieve job from particle input in the CoCo workbench. CoCo runs sieving with its bundled DFR reconstruction and postprocessing tools in the managed runtime. Selected particles can feed downstream reconstruction or CryoSPARC refinement jobs; no external RELION executables are required.

CryoPROS

A preferred-orientation correction framework for single-particle cryo-EM, using AI-generated auxiliary particles and co-refinement of synthesized and experimental data.

v1.0.1

What it does

CryoPROS addresses misalignment errors caused by preferred orientation in single-particle cryo-EM. It uses AI to generate auxiliary particles and performs co-refinement between synthesized and experimental data, correcting orientation bias that would otherwise degrade reconstruction.

  • AI-generated auxiliary particles for orientation diversity
  • Preferred-orientation correction across tilted views
  • Co-refinement of synthesized and experimental particle data
  • Misalignment error reduction for higher-fidelity maps

How it works

CryoPROS uses AI to generate auxiliary particles that compensate for preferred-orientation bias during cryo-EM reconstruction. These synthetic particles are co-refined with experimental data, producing a more isotropic orientation distribution and reducing misalignment errors.

Publication

"CryoPROS: Correcting misalignment caused by preferred orientation using AI-generated auxiliary particles"

Nature Communications, 2025

If CryoPROS contributes to your work, please cite the paper above.

How it fits in CoCo

CoCo organizes CryoPROS as connected Prep, Train, and Generate jobs. Use the managed runtime to prepare inputs, train the model, and generate auxiliary particles. A separate Export to CryoSPARC job can transfer completed outputs for further refinement.

Orientation correction Co-refinement

EModelG

Automated glycan and protein backbone modeling from cryo-EM density. EModelG combines AI detection, density fitting, and structural restraints to support studies of proteins, glycoproteins, and glycan-rich complexes.

Included in CoCo

Automated glycan modeling

Glycan diversity, flexibility, and complex linkages make structural modeling challenging. EModelG links AI detection with density-guided template fitting, joint optimization, and chain refinement.

  • Detect candidate glycan sites and fit monosaccharide templates to the density.
  • Optimize conformations and linkages using density correlation, chemical geometry, torsions, and clash restraints.
  • Build and refine chains for studies of glycofibrils, glycoproteins, and glycan-rich complexes.

Automated protein backbone modeling

EModelG combines AI detection, backbone tracing, and density validation to retain reliable long fragments and extend models using peptide-derived symmetry.

  • Preserve long backbone fragments supported by density and geometry, including when usable symmetry is unavailable.
  • Extend from fixed seeds with local density and backbone anchors to limit accumulated drift.
  • Model proteins independently or integrate protein and glycan models for joint structural analysis.

From density to a protein model

The PLL-1 example illustrates an automated protein model fitted into cryo-EM density. Protein scaffolds and glycan connectivity provide complementary views of complex assemblies.

Before install

Prerequisites

The packaged application and managed runtime target Linux x86_64 (amd64) with glibc 2.17 or newer. macOS is supported for source development, but cannot run this packaged runtime.

  • A writable installation directory with space for the release and extracted runtime.
  • bash, tar, gzip, awk, and date.
  • Java 8 or newer to run the backend.
  • Host Python 3 for runtime archive validation. Set PYTHON to another Python 3 executable if needed.
  • For GPU workflows, an NVIDIA GPU and a host driver compatible with the bundled CUDA 12.1 runtime.
  • A desktop browser with a viewport of at least 1024 × 768 for the CoCo application.
  • Access to the external services and shared storage used by your workflows.

The managed runtime supplies the Python environment and CUDA user-space dependencies. CryoSieve and CryoPROS use bundled CoCoShed packages. The installer also validates the bundled setsid executable.

Release archive

Extract the release

Place coco-0.3.5.tar.gz in an empty release directory and extract it there.

Terminal 
tar -xzf coco-0.3.5.tar.gz
cd coco

runtime/coco-version selects the matching runtime pack and environment. The installer checks the bundled environment specification and the compiled package inventory in cocoshed/manifest.json.

Use a fresh release directory

Extracting over an older release can leave obsolete files behind. For an existing installation, follow Backups and upgrades to preserve state and saved paths.

Bundled environment

Install the managed runtime

Run the installer from the extracted coco/ directory.

Terminal 
bin/coco-install-runtime.sh

The installer validates and extracts the runtime, checks the complete CoCoShed manifest, relocates the environment, and validates its commands, Python modules, and CUDA headers. It publishes these paths:

Installed paths 
runtime/envs/coco-runtime-0.3.5/
runtime/coco-runtime-profile.json

The runtime, profile, and CoCoShed files are updated together. A failed installation restores the previous installation.

Installer options

  • --check-only validates an existing environment and rewrites its profile. Use it for a later audit or diagnosis; a successful fresh installation has already completed validation.
  • --force replaces the selected version's runtime and CoCoShed inventory from the bundled release.
  • --root /absolute/path/to/coco specifies the installation root explicitly.
  • --run-cocoshed-smokes adds optional functional diagnostics during installation or audit. Their results are reported separately from runtime readiness.

--force and --check-only cannot be combined. Manifest and exact-inventory validation always run.

Launch

Start CoCo

Terminal 
cd /absolute/path/to/coco
java -jar backend/coco-0.3.5.jar

Open http://localhost:8078. Always start from the same coco/ working directory: project references, accounts, and site settings are stored relative to it. Run one active backend JVM for each project tree.

To use a different port, append --server.port=8080. If the runtime profile cannot be located automatically, specify it while keeping the same working directory:

Runtime profile override 
java -Dcoco.runtime.profile=/absolute/path/to/coco/runtime/coco-runtime-profile.json \
  -jar backend/coco-0.3.5.jar

Validation

Verify the installation

  1. Confirm runtime/envs/coco-runtime-0.3.5/ and runtime/coco-runtime-profile.json exist after installation.
  2. Start CoCo and confirm the interface loads at http://localhost:8078.
  3. Open Settings → Environment Check and confirm Managed CoCo Runtime reports READY.
  4. Configure and check external connections needed by your workflows.
  5. Configure a Local GPU, SLURM, or LSF lane for job execution.
Runtime status API 
GET /api/v1/managed-runtimes/current

Job submission also checks the capabilities required by that job. For example, Import Structure requires STRUCTURE and Auto Mask requires AUTO_MASK. Global runtime readiness alone does not replace these checks.

Application settings

Configure CoCo and authentication

Default settings are bundled in the backend JAR and can be overridden with Spring Boot command-line properties.

Defaults 
server.port=8078
server.servlet.session.timeout=24h
app.auth.mode=DISABLED
app.auth.users-file=auth/users.json
  • DISABLED treats every client as the local administrator. Use it on a trusted single-user host or isolated network.
  • BOOTSTRAP creates an administrator when the user store is missing or empty.
  • ENFORCED requires login for the interface and API. Create the initial administrator before enabling it; an empty user store prevents startup.

Run the following from the fixed coco/ working directory. Replace YOUR_TEMPORARY_PASSWORD with your chosen password.

Bootstrap an administrator 
java -jar backend/coco-0.3.5.jar \
  --app.auth.mode=BOOTSTRAP \
  --app.auth.bootstrap-admin-username=admin \
  --app.auth.bootstrap-admin-password='YOUR_TEMPORARY_PASSWORD' \
  --app.auth.bootstrap-admin-must-change-password=true
  1. Open http://localhost:8078/projects.
  2. Sign in at /login with the administrator account.
  3. Change the temporary password at /account/password when prompted.
  4. Continue to /projects.

Changing the bootstrap password in later launches does not overwrite an existing account. For an intentional reset, use:

One-time password reset 
java -jar backend/coco-0.3.5.jar \
  --app.auth.mode=BOOTSTRAP \
  --app.auth.bootstrap-admin-username=admin \
  --app.auth.reset-admin-password='YOUR_TEMPORARY_PASSWORD'

Remove the reset flag from future launches after resetting the password. Preserve auth/users.json; it is the account database. The default login-session idle timeout is 24 hours.

Site integration

Connect external services

Configure the services used by your workflows in Settings → Environment Check after the managed runtime reports READY.

Installation path · CryoSPARC 4 or 5

  1. Choose Installation path and enter the CryoSPARC installation path accessible from the CoCo host.
  2. As an administrator, run Check installation and confirm the detected version.
  3. In CryoSPARC Email, enter your account email and server URL, provide a password when requested, and run the account check.
  4. Confirm the expected projects and lanes are available.

Remote URL · CryoSPARC 5

  1. Choose Remote URL and enter the server root, for example https://cryosparc.example.org. Include the port if needed; omit page paths, queries, and fragments.
  2. Enter your CryoSPARC email and password, then select Check connection. The password creates a saved session; reconnect with your password if the session expires.
  3. Check data access as well as API connectivity. When shared storage has different mount paths, set the CoCo and CryoSPARC prefixes in Shared storage path mapping.

Path mapping describes shared files already available to both systems; it does not transfer data. Ensure the CoCo host can read the actual project directories.

CryoSeek WIT

WIT workflows need HTTPS access from the CoCo server to the CryoSeek WIT service. In CryoSeek WIT Connectivity, an administrator can configure Proxy Command and select Save and run WIT probe.

The default command is source /usr/local/bin/set_proxy.sh. To use the server's inherited network environment without extra setup, enter the nonempty Bash no-op :.

Structural modeling

Set up EModelG

The EModelG algorithm is bundled in CoCoShed. Its larger resource bundles are downloaded separately through Environment Check.

  1. Open Settings → Environment Check → EModelG Resources.
  2. Set Resource Directory to a writable installation root, for example /shared/emodelg. CoCo creates the version subdirectory automatically.
  3. Use the default Download Base URL, https://cocoproject.org.cn/emodelg/, or an HTTPS mirror serving the same fixed archive filenames.
  4. If needed, set the optional Proxy Command before downloading. Run the resource check and wait for download and verification to complete.
  5. Make the installed resources accessible at the same configured path from the backend and the selected compute nodes.

All EModelG modes require both resource bundles: 21 SO(3) libraries and three checkpoints. CoCo verifies them against its bundled catalog. Rerun Environment Check for an existing resource installation when upgrading to this release.

Phenix for glycan modeling

Glycan (+ protein) modeling (full) also requires a separately installed Phenix. In the Phenix card, set Installation Path and run Check. The optional Environment Command runs before Phenix activation during both the check and job execution.

Phenix and any paths used by its environment command must be accessible from the backend and compute nodes. Protein modeling and Protein modeling (preserve existing glycans) do not require Phenix.

One node and one GPU per EModelG job

Select a lane with one available GPU. Preserve-existing-glycans mode requires a glycan-only input structure; a structure containing protein CA atoms is rejected. Clear or Restart begins a fresh attempt from the start.

Host execution

Configure Local GPU lanes

Open Settings → Cluster Configuration, create a Local GPU lane, and choose the concrete devices in Local GPU Pool. Refresh the inventory after hardware changes.

  • The CoCo host needs the NVIDIA driver and nvidia-smi for GPU discovery.
  • The selected pool size limits the GPUs a job may request.
  • Local GPU execution uses one host; requests for more than one node are rejected.
  • Jobs run as the backend account. That account must be able to read inputs and the runtime, and write project and job outputs.

Local GPU lanes do not require a scheduler client. CoCo activates the managed runtime for each job.

Cluster execution

Configure SLURM lanes

In Settings → Cluster Configuration, set Max GPUs per Node to the lane's per-node capacity. Choose node count, GPUs per node, and CPU budget in each job dialog.

Put fixed site settings such as partition, account, time, memory, and CPU defaults in Cluster Template. Adapt this example to your cluster:

Example cluster template 
#!/bin/bash
#SBATCH --partition=<gpu_partition>
#SBATCH --mem=128G
#SBATCH --cpus-per-task=8

CoCo generates job names, stdout/stderr paths, node/task layout, and GPU requests. Leave those directives out of the template. Use Local Environment for required site setup such as module load commands.

For distributed torchrun jobs, CoCo starts one SLURM task per node, then one worker per requested GPU. Two nodes with four GPUs each use two SLURM tasks and eight GPU workers.

The job's CPU budget is per node and shared by its GPU workers. A typed job CPU budget overrides lane CPU settings. Avoid activating another Conda environment or launching torchrun or mpirun in Local Environment.

Cluster execution

Configure LSF lanes

Use IBM Spectrum LSF 10.1 Fix Pack 9 or newer. Run the CoCo backend directly on the submission host, with these commands available to its service account in the same non-interactive startup environment:

Client check 
command -v bsub blaunch bjobs bhist bkill

The cluster must enable LSB_GPU_NEW_SYNTAX=extend and provide task-level CUDA_VISIBLE_DEVICES<number> bindings. Ask the cluster administrator to verify these settings; GPU requests using nocvd are incompatible.

Set Max GPUs per Node to the lane's capacity. Keep only fixed queue, project, wall-time, memory, and site constraints in Cluster Template:

Example cluster template 
#!/bin/bash
#BSUB -q <gpu_queue>
#BSUB -P <project_name>
#BSUB -W 24:00

Leave job identity, log paths, slot and host counts, span[...], and GPU requests to CoCo. Do not add -outdir, interactive submission flags, or GPU constraints in -R.

For jobs with a typed CPU budget, CoCo requests nodes × CPUs per node slots and places that CPU budget on each host. blaunch starts one launcher per allocated host, then one worker per requested GPU.

Shared paths and submission environment

The backend and compute nodes must resolve the same absolute CoCo, runtime, CoCoShed, project, and job paths. Initialize the LSF client before starting Java; a lane's Local Environment runs too late to configure backend submission commands.

Job execution

Runtime behavior

You can prepare job drafts before the runtime is installed. Submission requires a READY runtime and the capabilities needed by the selected job.

Generated scripts activate the versioned runtime automatically for Local GPU, SLURM, and LSF execution. Legacy lane activationCmd settings are ignored.

Retain older runtime/envs/coco-runtime-<version>/ directories when saved scripts still reference them. Their absolute paths are part of the saved execution context.

Installation lifecycle

Backups and upgrades

Keep the same installation path and backend working directory across upgrades. With default settings, these directories inside coco/ contain persistent operator state:

  • projectConfig/ — registered project references.
  • pageParam/ — saved page parameters and scheduler lanes.
  • path/ — external connection settings.
  • auth/ — users, CryoSPARC sessions, profiles, and path mappings.
  • settings/ — artifact-signing key and SSD cache settings.
  • bookmarks/ and user-settings/ — filesystem bookmarks and user preferences.

If the user-store or artifact-signing-key location is overridden, back up its actual path. CryoSPARC account state follows the user-store parent directory. Project and job data may be outside the installation; back up those directories too. projectConfig/ stores references to them.

  1. Stop new submissions. Let active jobs finish or cancel them with the current backend, and confirm their terminal state.
  2. Stop the backend JVM and back up application state, project/job data, and runtime trees you need to retain.
  3. Extract the new release into an empty staging directory. Replace release-owned artifacts at the original installation path, accounting for obsolete files while preserving state and existing runtime/envs/ trees.
  4. Run the new runtime installer at the final installation path. For an existing selected-version environment, use --check-only for intentional reuse or --force to replace it. Resolve validation errors before restarting.
  5. Restart from the same working directory and follow Verify the installation.

Install the runtime at its final path; do not install it in a staging directory that will later be moved.

Optional acceptance

Workflow checks

Choose end-to-end checks that apply to your site, especially after changing the runtime or compute lanes. These complement the fresh-install verification.

  1. Import particles, then create Restack Particles, DFR reconstruction, or CryoSieve jobs from the particle output.
  2. Where CryoSPARC is configured, test refinement and B-factor analysis from CryoSieve outputs.
  3. Connect CryoPROS Prep → Train → Generate.
  4. Run Export to CryoSPARC from a completed CryoPROS Generate or Select 2D job. Confirm it creates and waits for one CryoSPARC Import Particles job.
  5. For EModelG, verify the resources, submit a one-node, one-GPU job, and inspect the available structures, summary, and review warnings. Retry loading refreshes saved result data without rerunning the computation.
  6. Submit and monitor a representative job through each configured lane. Verify a multi-node LSF job and its blaunch startup before enabling that execution mode for users.

Recovery

Troubleshooting

Port 8078 is already in use

Start from the fixed coco/ directory with java -jar backend/coco-0.3.5.jar --server.port=8080, then open that port.

Runtime pack or matching metadata is missing

Use a complete release containing runtime-packs/coco-runtime-0.3.5.tar.gz and runtime/runtime-environment.yml. A provenance-field error can indicate mixed installer and runtime versions; deploy the matching backend, helpers, metadata, and CoCoShed together.

Managed runtime is MISSING, ERROR, or INCOMPLETE

Run bin/coco-install-runtime.sh --check-only. If files are missing or stale, reinstall with --force, then refresh Environment Check. Check-only reports undeclared CoCoShed artifacts instead of cleaning them.

The backend cannot find the runtime profile

Confirm runtime/coco-runtime-profile.json exists and that Java starts from the extracted coco/ directory. Use the explicit profile option under Start CoCo if needed.

CryoSPARC connects, but project files cannot be read

Verify shared mounts, permissions, and path mappings from the CoCo host. For an expired saved session, reconnect with the account password. An API connection check does not establish filesystem access.

EModelG resources or Phenix checks fail

Check the resource directory's permissions, HTTPS or proxy access, and mirror filenames. Rerun the resource check to download and verify both bundles. For full mode, verify Phenix and its environment command on the backend and compute nodes.

LSF submission, status, or cancellation fails

Check bsub, blaunch, bjobs, bhist, and bkill as the backend account in its startup environment. Inspect bjobs -l <job_id> and bhist -l <job_id>. Verify site GPU bindings and shared paths, and remove conflicting template resource directives.

Cluster execution

Configure SLURM lanes

Open Settings → Cluster Configuration. A lane stores the fixed settings of a queue or partition; each job chooses its node count and GPUs per node.

  • Max GPUs: the maximum GPUs per node a job may request. Set it to 4 for a node with four available GPUs.
  • Cluster Template: fixed partition, account, wall time, memory, and CPU settings.
  • Local Environment: execution-host setup such as site-provided CUDA modules. CoCo activates its Python runtime automatically.
Example fixed lane template 
#!/bin/bash
#SBATCH --partition=<gpu_partition>
#SBATCH --mem=128G
#SBATCH --cpus-per-task=8

Leave job name, stdout/stderr paths, node count, task count, and GPU requests out of the template. CoCo generates them for each job, including --gpus-per-node. A distributed torchrun job uses a task count of nodes × GPUs per node.

Requests above the lane’s Max GPUs are rejected. Do not activate another conda environment or start an extra distributed launcher in the lane setup.

Lane administration

Lane templates execute shell commands as the backend or job account. Give lane editing access to trusted administrators. With authentication disabled, use a trusted single-user host or an isolated network.

Cluster execution

Configure LSF lanes

CoCo supports IBM Spectrum LSF 10.1 Fix Pack 9 or newer. Run the backend directly on an LSF submission host. In the service account and non-interactive environment that starts Java, confirm these commands are available:

Check the backend environment 
command -v bsub blaunch bjobs bhist bkill

Initialize the site’s LSF client before starting CoCo. A lane’s Local Environment runs inside the submitted job and cannot supply missing scheduler commands to the backend. CoCo submits directly from the host and does not provide an SSH hop.

  • Enable cluster GPU resources and LSB_GPU_NEW_SYNTAX=extend. Fix Packs 9–12 require explicit administrator configuration; Fix Pack 13 and newer use it by default.
  • Provide task-level CUDA_VISIBLE_DEVICES<number> variables. A merged mps=...,nocvd setting is incompatible with CoCo’s GPU binding.
  • Make the CoCo installation, runtime, modules, project directories, and job directories available at identical absolute paths on the submission host and every execution host.
  • Give the backend and job accounts read/execute access to the installation and read/write access to project and job data. The backend account must be able to submit, query, cancel, and use blaunch.
Example fixed lane template 
#!/bin/bash
#BSUB -q <gpu_queue>
#BSUB -P <project_name>
#BSUB -W 24:00

Set Max GPUs to the lane’s limit per host. Each job chooses its host count and GPUs per host. CoCo generates job identity, logs, slot placement, and GPU allocation, then uses blaunch to start the workers.

Keep job name, output paths, -outdir, -n, -nnodes, -hostfile, span[...], -gpu, and GPU constraints in -R out of the template. Synchronous or interactive options -K, -I, -Ip, and -Is are unsupported.

Keep blaunch available inside the allocation. Lane setup may load site modules, but must not activate a separate Python environment or pre-launch mpirun or torchrun. Verify a representative job on each lane, including a multi-node job if that lane will support one.

Plan downstream jobs in advance, manage multiple jobs together, and connect particle processing, reconstruction, and CryoSPARC export within one project.

Previous v0.2.0 Released v0.3.2

Workflow continuity

Keep workflows moving, with room for review.

CoCo v0.3.2 builds on the project workflow introduced in v0.2.0. Jobs can run in sequence when no human review is required, while researchers can still inspect results and choose outputs at key stages.

01

Task dependencies

Create downstream jobs before upstream work finishes.

In v0.2.0, an upstream job had to finish before a downstream job could be created. With v0.3.2, researchers can configure later steps and their dependencies while upstream work is still in progress.

  • Downstream jobs can start automatically after upstream jobs finish, when no human review is required.
  • For steps that need judgment, review upstream results and select outputs before deciding how to proceed.
  • Jobs and their dependencies remain visible in the project view for tracing inputs and reviewing the processing history.

For example, prepare a reconstruction job while particle selection is running. Once selection finishes, reconstruction can continue automatically if the selected particles do not need manual review.

02

Batch operations

Handle related jobs together.

Select multiple visible jobs in a project and apply the supported batch operations. Jobs and their dependency links stay in view, helping researchers make selections in context.

  • Manage several jobs within the same workflow through one selection.
  • Before submitting jobs in a batch, check that each job's execution queue is appropriate for its requirements.

Reconstruction and export

Choose the next analysis step explicitly.

03

Separate DFR and SGD reconstruction options

The generic Reconstruct entry is now split into 3D Reconstruction (DFR) and 3D Reconstruction (SGD). Choose the reconstruction path when creating a job, then connect it to particle processing and algorithm analysis in the same project.

04

A dedicated Export to CryoSPARC job

Export to CryoSPARC is now an independent workflow job that can follow particle processing, CryoSieve, CryoPROS, or 3D reconstruction. Pass outputs to CryoSPARC for further analysis while keeping upstream relationships visible in CoCo.

Before install

Prerequisites

Required runtime tools:

  • Java 8 or above
  • Access to CryoSPARC, if using CryoSPARC-backed jobs
  • Access to RELION, if using RELION-backed jobs

CoCo itself is packaged as a Spring Boot jar with the built frontend embedded. CryoSieve and CryoPROS use CoCo's managed runtime installed from runtime-packs/coco-runtime.tar.gz; users should not prepare separate CryoSieve or CryoPROS Python environments.

cd coco

Managed environment

Install the managed runtime

From the unpacked coco/ directory, install the unified CryoSieve and CryoPROS runtime.

Terminal 
bin/coco-install-runtime.sh

This unpacks runtime-packs/coco-runtime.tar.gz, runs conda-unpack, validates the CryoSieve and CryoPROS command-line tools, and prepares the managed runtime under:

Runtime path 
runtime/envs/coco-runtime

It also writes the runtime profile consumed by CoCo:

Profile path 
runtime/coco-runtime-profile.json

If the runtime already exists, validate it and rewrite the profile:

Check existing runtime 
bin/coco-install-runtime.sh --check-only

To remove and reinstall the runtime:

Reinstall runtime 
bin/coco-install-runtime.sh --force

Launch

Start CoCo

Use the jar found under backend/.

Terminal 
java -jar backend/<backend runnable jar>

You may also start from the parent directory, which is useful when existing project or auth data is relative to that working directory.

Parent directory 
java -jar coco/backend/<backend runnable jar> --server.port=8078

In packaged releases, CoCo first checks ./runtime/coco-runtime-profile.json, then infers coco/runtime/coco-runtime-profile.json from the jar location. If needed, override the runtime profile explicitly.

Runtime override 
java -Dcoco.runtime.profile=/absolute/path/to/coco/runtime/coco-runtime-profile.json \
  -jar coco/backend/<backend runnable jar> --server.port=8078

The default backend port is 8078. Open:

Browser 
http://localhost:8078

Settings

Configuration

Default application settings are bundled in the jar:

application.properties 
server.port=8078
app.auth.mode=DISABLED

To override settings at runtime, provide Spring Boot properties. For example, to use another port:

Custom port 
java -jar backend/<backend runnable jar> --server.port=8080

To enable auth, use one of the supported modes:

Bootstrap auth 
java -jar backend/<backend runnable jar> \
  --app.auth.mode=BOOTSTRAP \
  --app.auth.bootstrap-admin-username=admin \
  --app.auth.bootstrap-admin-password=change-me

Supported auth modes:

  • DISABLED
  • BOOTSTRAP
  • ENFORCED

When auth is enabled, file-based users are stored under auth/users.json, relative to the process working directory.

Auth flow

Login verification page

When auth is enabled, protected pages redirect unauthenticated users to /login-verification. Use the configured account and password to sign in.

For a fresh release test with bootstrap auth:

Bootstrap test 
java -jar backend/<backend runnable jar> \
  --server.port=8078 \
  --app.auth.mode=BOOTSTRAP \
  --app.auth.bootstrap-admin-username=admin \
  --app.auth.bootstrap-admin-password=ChangeMe123 \
  --app.auth.bootstrap-admin-must-change-password=true

Then open:

Browser 
http://localhost:8078/home
  1. /home redirects to /login-verification.
  2. Sign in with account admin and password ChangeMe123.
  3. If mustChangePassword is true, CoCo redirects to /change-password.
  4. After changing the password, CoCo opens /home.

BOOTSTRAP only creates the bootstrap admin when auth/users.json is missing or empty. If auth/users.json already contains users, changing app.auth.bootstrap-admin-password does not overwrite the existing admin password.

To reset the bootstrap admin password intentionally:

Reset admin password 
java -jar backend/<backend runnable jar> \
  --server.port=8078 \
  --app.auth.mode=BOOTSTRAP \
  --app.auth.bootstrap-admin-username=admin \
  --app.auth.reset-admin-password=ChangeMe123

After reset, sign in with admin / ChangeMe123. CoCo will require a password change.

Disposable local tests only

You can remove the test user file and bootstrap again only for disposable local tests.

Local reset 
rm -f auth/users.json
java -jar backend/<backend runnable jar> \
  --server.port=8078 \
  --app.auth.mode=BOOTSTRAP \
  --app.auth.bootstrap-admin-username=admin \
  --app.auth.bootstrap-admin-password=ChangeMe123

Do not delete auth/users.json in production unless you intend to remove the stored users.

Compute lanes

Configure SLURM lanes

CoCo lanes describe how jobs are submitted to a compute environment. For a SLURM lane, the lane should contain the fixed SLURM template for that queue or partition, while per-job resources such as GPU count are chosen in each job dialog.

Single-node SLURM lane with job-selected GPU count

For a single-node GPU lane where different jobs may request different GPU counts, configure the lane as a capacity limit instead of a fixed GPU request.

  • Max GPUs: set this to the maximum number of GPUs a job may request on this lane. For example, if one node has 4 GPUs, set Max GPUs = 4.
  • Cluster Template: include only fixed SLURM settings for this lane, such as partition, memory, stdout, and stderr paths.
  • Local Environment: include shell setup lines such as module load commands.
  • Do not put fixed node, task, or GPU resource requests in the lane template.

Avoid these lines in the SLURM lane template:

Avoid fixed requests 
#SBATCH -N 1
#SBATCH --nodes=1
#SBATCH -n 1
#SBATCH --ntasks=1
#SBATCH --gpus=1
#SBATCH --gpus-per-node=1
#SBATCH --gpus-per-task=1
#SBATCH --gres=gpu:1

CoCo generates those resource lines dynamically from the job dialog. For GPU jobs, the job dialog determines the requested GPU count, and CoCo writes a single-node SLURM header like:

Generated by CoCo 
#SBATCH -N 1
#SBATCH --ntasks=<task-count>
#SBATCH --gpus=<job num_gpus>
export COCO_NUM_GPUS=<job num_gpus>
export COCO_NPROC_PER_NODE=<job num_gpus>

Example SLURM lane for a single-node GPU partition with up to 4 GPUs:

Cluster template 
#!/bin/bash
#SBATCH --partition=<gpu_partition>
#SBATCH --mem=128G
#SBATCH --output=coco-%j.out
#SBATCH --error=coco-%j.err

Set:

Lane capacity 
Max GPUs: 4

Then each job chooses its actual GPU count in the job creation dialog:

  • job requests 1 GPU, CoCo adds #SBATCH --gpus=1
  • job requests 2 GPUs, CoCo adds #SBATCH --gpus=2
  • job requests 4 GPUs, CoCo adds #SBATCH --gpus=4

If the job requests more GPUs than the lane's Max GPUs, CoCo rejects the submission.

Example Local Environment:

Local environment 
module purge
module load cuda/12.1
module load relion

For CryoSieve and CryoPROS jobs, do not activate a separate Python or conda environment in the lane. CoCo activates the managed runtime automatically.

Runtime rules

Managed runtime behavior

Jobs that require the managed runtime include:

  • RESTACK_PARTICLES
  • CRYOSIEVE
  • CSREFINE
  • CSRHBFACTOR
  • CRYOPROS_PREP
  • CRYOPROS_TRAIN
  • CRYOPROS_GENERATE

Draft creation and editing are allowed when the runtime is missing, so users can prepare jobs before installation. Submit Now and existing draft submit are blocked until the runtime status is READY. Generated bash and SLURM scripts automatically activate runtime/envs/coco-runtime; for managed jobs, any old activationCmd value is ignored to avoid activating a different environment.

Release checks

Runtime workflow checks

After installation, test these flows in a real project:

  1. Import a PARTICLE job.
  2. Create RESTACK_PARTICLES from PARTICLE.
  3. Create RECONSTRUCT from PARTICLE or RESTACK_PARTICLES.
  4. Create CRYOSIEVE from PARTICLE or RESTACK_PARTICLES.
  5. Create CSREFINE and CSRHBFACTOR from CRYOSIEVE.
  6. Create CRYOPROS_PREP from PARTICLE or RESTACK_PARTICLES.
  7. Create CRYOPROS_TRAIN from CRYOPROS_PREP.
  8. Create CRYOPROS_GENERATE from CRYOPROS_TRAIN.
  9. If using CryoSPARC export, enable export in CRYOPROS_GENERATE and confirm export_cryopros.py is resolved from the CryoPROS module resource or classpath fallback.

Troubleshooting

Common release checks

Port already in use

Start on another port:

Terminal 
java -jar backend/<backend runnable jar> --server.port=8080

Managed runtime is MISSING, ERROR, or INCOMPLETE

Run from the unpacked coco/ directory:

Check runtime 
bin/coco-install-runtime.sh --check-only

If validation fails because files are missing or stale, reinstall:

Force reinstall 
bin/coco-install-runtime.sh --force

Then restart or refresh CoCo and check Settings → Environment Check → Managed CoCo Runtime.

CryoSPARC or RELION commands fail

Reopen Settings → Environment Check and verify the configured shell snippets. New lanes should use external dependency environment setup only; CryoSieve and CryoPROS are handled by the managed runtime.

CryoSieve movie is missing

This is expected. cryosieve_video_tutorial.mp4 is intentionally excluded from the release package and is not required for CoCo runtime.

Module resources are missing

Check that the unpacked release still contains:

Required resources 
modules/cryosieve/module.yaml
modules/cryosieve/jobTypeMapping.json
modules/cryopros/module.yaml
modules/cryopros/jobTypeMapping.json
modules/cryopros/scripts/export_cryopros.py
modules.lock

Fresh source clone cannot fetch submodule commit

If installing from source rather than from coco.tar.gz, make sure the submodule commits recorded in modules.lock have been pushed to their remotes. Otherwise git submodule update --init --recursive or packaging/validate-modules.js remote reachability checks may fail.
